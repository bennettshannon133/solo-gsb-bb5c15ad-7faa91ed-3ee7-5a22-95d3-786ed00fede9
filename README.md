# 过敏原残留追踪（Allergen Residue Tracker）

为**共用设备的小型食品加工车间**设计的 Web 应用：按时间录入每个批次的配方过敏原、依次使用的设备以及设备清洗记录，系统逐步推演每台设备上的过敏原残留，回答两个核心问题：

1. **每个批次最终含哪些过敏原？**（配方自带 + 从共用设备交叉污染继承）
2. **每种继承到的过敏原是从哪来的？**（可逐步展开的传播来源链，逐层追溯到某个批次的配方源头）

此外，在「📊 推演结果」页提供两个**只读试算**入口（不落库、不产生新 ID）：

- **🧹 清洗规划**：选择一种过敏原与一个或多个目标批次，录入最多 10 个候选清洗位置（设备 + 时间），系统搜索候选位置的子集，给出使所有目标批次最终均不含该过敏原的**清洗次数最少**的新增清洗方案。
- **🗓️ 批次改期影响预览**：选择一个现有批次并输入新的批次时间，系统把该批次所有**填写了时间**的设备步骤按「新批次时间 − 原批次时间」的分钟差整体平移（**留空步骤**继续沿用新批次时间），**其他批次与全部清洗记录保持原样**，在内存中复用现有推演，逐批列出改期前后**新增 / 消失的交叉污染过敏原**与**改期后的最终过敏原集合**。

技术栈：Node.js + Express（后端/API/推演引擎）+ 原生 HTML/CSS/JavaScript 前端（无框架、无打包步骤），JSON 文件持久化（无需数据库）。

## 一条命令启动

```bash
docker compose up --build
```

启动完成后浏览器打开：

> **http://localhost:3000**

- 端口：容器内 `3000`，映射到宿主机 `3000`（修改 `docker-compose.yml` 中 `"3000:3000"` 可改宿主机端口）。
- 依赖安装、数据目录初始化均在镜像构建/容器启动时自动完成，无需手动执行任何初始化脚本。
- 首次启动会自动写入一套**演示数据**（4 台设备、3 个批次、2 条清洗记录，便于立即看到跨污染链路）；数据保存在 Docker volume `allergen-data` 中，重启不丢失。不想预置数据时，删除 `docker-compose.yml` 里的 `SEED_DEMO` 环境变量即可。

停止：`Ctrl+C`（后台运行用 `docker compose up -d`，停止并删除容器用 `docker compose down`）。

## 本地直接运行（不用 Docker）

要求 Node.js ≥ 18。

```bash
npm install
npm start
```

同样访问 **http://localhost:3000**。数据文件默认在 `./data/db.json`（首次启动自动创建）。

可选环境变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | 监听端口 |
| `DATA_FILE` | `./data/db.json` | JSON 数据文件路径 |
| `SEED_DEMO` | 未设置 | 设为 `1` 时，启动若发现库为空则自动灌入演示数据 |

## 推演规则（模型说明）

所有「批次步骤」和「清洗记录」按时间混排成一条时间线，从头逐步模拟：

1. **批次接触设备（先继承，后留渍）**
   - 批次先把设备上**已有、而自己尚未携带**的过敏原**继承**到自身；
   - 再把自身当前携带的全部过敏原（配方过敏原 + 此前各步继承到的）**留渍**到该设备上，后续设备和批次可继续继承。
   - 同一步内刚留下的残留不会被自己重复继承。
2. **清洗只移除所选过敏原**：勾选哪些就移除设备上的哪些；未勾选的原样保留。勾选了当时设备上并不存在的过敏原时，该次清洗对该过敏原无效（界面会明确标出）。
3. **同一分钟**内既有清洗又有批次接触时，**清洗先执行**（视为接触前的换产准备）。
4. 步骤时间留空时回退使用批次时间。

页面提供：

- **残留传播时间线**：每个清洗/接触事件可展开查看事件后的设备残留快照、本步继承明细与来源；
- **各批最终过敏原**：区分「配方自带 / 交叉污染继承」，每种过敏原可逐级展开来源链
  （例：C 批在烤箱继承小麦 → 该小麦来自 B 批次从搅拌缸带来 + A 批次直接留渍 → 根源是 A 批配方）；
- **🧹 清洗规划**（见下节）；
- **🗓️ 批次改期影响预览**（见下节）；
- **设备最终残留**：推演结束时每台设备上的残留及其来源；
- **修改即重推演**：任何记录的新增、编辑、删除（含删除设备时的级联清理）后，服务端立即基于全部记录重新推演并返回；也可点右上角「↻ 重新推演」手动刷新。

## 清洗规划（只读试算）

在「📊 推演结果 → 🧹 清洗规划」中：

1. **单选一种过敏原**；
2. **勾选一个或多个目标批次**（要求它们的最终过敏原集合都不含该过敏原）；
3. 录入**最多 10 个候选清洗位置**（每个位置 = 设备 + 时间，可附备注），位置的输入序号即并列裁决时的字典序，可用 ↑/↓ 调整。

提交 `POST /api/cleaning-plans` 后，系统把候选位置的每个子集当作「仅移除所选这一种过敏原的虚拟清洗」追加到现有时间线，**复用同一个推演引擎**重新推演（因此批次先继承后留渍、同分钟清洗先于接触、清洗只移除勾选过敏原等规则完全一致）：

- 在所有可行子集中返回**清洗次数最少**的方案；次数并列时，按候选输入序号列表的字典序取一个（如 `[1,4]` 优先于 `[2,3]`）；
- **无需新增清洗**时（所有目标批次本来就不含该过敏原）返回**空方案**；
- **无解时明确提示原因**：候选位置任意子集都无法满足时，提示位置必须早于目标批次接触带残留设备的时刻；
- **配方自带的过敏原不能被清洗消除**：任一目标批次的配方含所选过敏原时直接判定无解并点名批次；
- 结果中展示**选用的清洗位置**以及每个目标批次**规划前 / 规划后的过敏原集合**；
- 规划**不会写入或修改任何原始记录**：全程只读取当前数据做内存试算，不落盘、不产生新 ID。

候选最多 10 个（最多枚举 2¹⁰ = 1024 个子集），每个子集一次完整推演，车间规模下即时返回。

## 批次改期影响预览（只读试算）

在「📊 推演结果 → 🗓️ 批次改期影响预览」中：

1. **选择一个现有批次**；
2. **输入新的批次时间**（格式 `YYYY-MM-DDTHH:MM`，与录入一致，分钟精度）。

提交 `POST /api/reschedule-preview` 后，系统在内存中对该批次做如下时间变换并**复用同一个推演引擎**重新推演：

- 该批次中**填写了时间的设备步骤**，一律按「新批次时间 − 原批次时间」的**分钟差整体平移**（跨日、跨月同样按挂钟分钟计算，例如 `09-30 23:50 → 10-02 00:10`）；
- **步骤时间留空**的步骤不平移，推演时继续回退使用**新批次时间**（与规则 4 一致）；
- **其他批次的时间与步骤、全部清洗记录保持原样**。

因此批次「先继承后留渍」、同分钟清洗先于接触（改期后的步骤若与某条清洗落在同一分钟，仍由清洗先执行）、清洗只移除勾选过敏原等规则完全一致。返回结果包括：

- `rescheduled`：改期批次、原时间、新时间与分钟差（正数为延后、负数为提前）；
- `shiftedSteps`：该批次每个设备步骤的改期前 / 改期后时间，并标明是「按分钟差平移」还是「留空沿用新批次时间」；
- **逐批对比 `batches`**（按改期后的时间顺序，覆盖所有批次）：
  - `addedCrossAllergens`：**新增的交叉污染过敏原**（改期后的继承过敏原 − 改期前）；
  - `removedCrossAllergens`：**消失的交叉污染过敏原**（反向差集）；
  - `afterFinalAllergens` / `beforeFinalAllergens`：**改期后 / 改期前的最终过敏原集合**（配方自带 ∪ 交叉污染继承），另附 `recipeAllergens`；
  - `changed` 标记该批交叉污染集合是否发生变化。
- 配方自带过敏原不会因改期而增减；只有交叉污染继承关系会随事件顺序变化。

预览**不会写入或修改任何原始记录**：全程只读取当前数据，在防御性深拷贝的内存副本上平移与试算，不落盘、不产生新 ID，重复调用与并发调用都不会改动原始记录。批次不存在或新时间缺失 / 格式不合法时返回 400 与明确中文错误。

## 页面结构

- **📊 推演结果**：时间线 / 批次最终过敏原与来源链 / **🗓️ 批次改期影响预览（只读试算）** / **🧹 清洗规划入口（只读试算）** / 设备最终残留
- **📦 批次录入**：批次名称、时间、配方过敏原（内置 9 种常见过敏原 + 可自定义）、按顺序排列的设备步骤（每步可选时间与备注，可上下调整顺序）
- **🧽 清洗记录**：设备、时间、本次移除的过敏原勾选、备注
- **⚙️ 设备管理**：设备增删改；删除设备会同步清理相关步骤与清洗记录并重新推演；可一键载入演示数据

## HTTP API

页面与 API 由同一服务、同一端口提供：容器启动后地址为 **http://localhost:3000**（页面 `GET /`，接口前缀 `/api`，如 `http://localhost:3000/api/state`）。宿主机端口可在 `docker-compose.yml` 的 `"3000:3000"` 处调整。

所有写操作成功后都返回完整的最新状态（`{ data, knownAllergens, trace }`），前端据此整体重渲染。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 原始记录 + 已知过敏原 + 推演结果 |
| POST/PUT/DELETE | `/api/equipment[/:id]` | 设备增改删（删除有级联） |
| POST/PUT/DELETE | `/api/batches[/:id]` | 批次增改删（含步骤） |
| POST/PUT/DELETE | `/api/cleanings[/:id]` | 清洗记录增改删 |
| POST | `/api/cleaning-plans` | 清洗规划（**只读试算，不写库**） |
| POST | `/api/reschedule-preview` | 批次改期影响预览（**只读试算，不写库**） |
| POST | `/api/seed-demo` | 空库时灌入演示数据（非空返回 409） |

### `POST /api/cleaning-plans` 请求与响应

请求体：

```json
{
  "allergen": "小麦（含麸质）",
  "batchIds": ["b_xxx", "b_yyy"],
  "candidates": [
    { "equipmentId": "eq_xxx", "time": "2026-09-25T08:45", "note": "可选备注" }
  ]
}
```

- `allergen`：必填，单一过敏原名称；`batchIds`：必填，一个或多个已存在的批次（重复会去重）；
- `candidates`：必填数组，长度 0–10；每项的设备必须存在，时间格式为 `YYYY-MM-DDTHH:MM`（同分钟清洗自动先于批次接触）。

响应体 `{ "plan": { ... } }`，`plan.status` 取值：

| status | 含义 |
| --- | --- |
| `solved` | 找到最优方案；`cleaningCount` 为最少清洗次数，`positions` 为选用位置（带候选序号 `candidateIndex`） |
| `already-clean` | 空方案：目标批次规划前均已不含该过敏原，`positions` 为空 |
| `unsolvable` | 无解：`message` 区分「配方自带不可消除」与「候选位置子集均无法满足」 |

`plan.batches` 给出每个目标批次规划前的 `beforeAllergens`、规划后的 `afterAllergens`、`recipeAllergens` 及 `allergenInRecipe` 标记。参数不合法返回 400（中文错误说明）。该接口只读，不影响 `GET /api/state` 返回的原始记录。

### `POST /api/reschedule-preview` 请求与响应

请求体：

```json
{
  "batchId": "b_xxx",
  "newTime": "2026-09-25T14:00"
}
```

- `batchId`：必填，必须是当前已存在的批次（否则 400「选择的批次不存在」）；
- `newTime`：必填，格式 `YYYY-MM-DDTHH:MM`（分钟精度；缺失、为空或非法日期 / 时间均返回 400 中文错误）。

响应体 `{ "preview": { ... } }`：

- `preview.rescheduled`：`{ batchId, name, oldTime, newTime, deltaMinutes, direction }`（`deltaMinutes` 正为延后、负为提前、0 表示时间未变）；
- `preview.shiftedSteps`：改期批次每个步骤的 `{ stepIndex, equipmentId, equipmentName, explicit, oldTime, newTime }`；`explicit=true` 表示按分钟差平移，`false` 表示原步骤留空、`newTime` 即新批次时间；
- `preview.batches`：所有批次（按改期后时间顺序）的对比：`{ batchId, name, rescheduled, oldTime, newTime, recipeAllergens, beforeFinalAllergens, afterFinalAllergens, addedCrossAllergens, removedCrossAllergens, changed }`；
- `preview.unchangedBatches` / `preview.unchangedCleanings`：未参与平移的其他批次数与清洗记录数（用于核对「其他批次及清洗时间保持原样」）。

该接口只读：不修改、不写入任何原始记录，不影响 `GET /api/state`。

## 说明与边界

- 定位为小型车间单机工具：持久化采用 JSON 文件 + 原子改名写入，适合低并发的录入场景；未引入数据库与用户体系。
- 残留模型是**定性**的（有/无该过敏原及其来源），不建模残留量与清洗效率百分比；清洗对过敏原是「移除 / 不移除」的确定性结果。
- 清洗规划是**无状态的只读试算**：候选清洗只存在于当次推演中（使用独立前缀的临时 ID），不经过持久化写入路径，重复调用与并发调用都不会改动原始记录。
- 批次改期影响预览同样是**无状态的只读试算**：只对读取出的数据做防御性深拷贝，在副本上平移所选批次的时间并复用 `trace()` 推演两次（改期前 / 改期后），原始批次时间、步骤时间与清洗记录均不被改写，重复调用与并发调用互不影响。
